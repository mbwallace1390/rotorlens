# Architecture and provenance boundary

## Purpose

RotorLens is an independent product experiment for locally inspecting supported
flight-controller logs. This document records where every current artifact came
from and establishes boundaries for future work. It is an engineering provenance
record, not a legal opinion or a claim of a formal clean-room process.

## Allowed inputs

- Product requirements written specifically for RotorLens.
- Public behavior and interoperability requirements expressed without copied
  implementation details. File formats, header keys, and field names are
  interoperability facts, not protected expression.
- Documentation, API information, source, and tests from a **permissively
  licensed** engine that has been formally adopted in
  `config/parser-engine-decision.json`, with attribution retained.
- Fixtures generated by `tools/generate-fixtures.mjs`.
- Test logs recorded by the project owner, or received under an explicit license
  and consent suitable for redistribution.

## Excluded product inputs

- Rotorflight Blackbox or Betaflight Blackbox Log Viewer GPL source code in
  RotorLens-authored application source or a shipping build.
- Their HTML, CSS, JavaScript, native wrappers, icons, images, translations,
  screenshots, UI wording, layouts, or architecture documentation.
- Mechanical translations, rewrites, or ports of GPL implementation code.
- Logs without clear consent, provenance, and privacy review.

## Reserved non-shipping viewer integration boundary

`integration/rotorflight-blackbox/0001-consume-rotorlens-pid-evidence.patch`
is the only location in this repository containing Rotorflight Blackbox viewer
context or modifications. It exists to apply the independently generated
RotorLens analysis bundle to the separate GPL viewer fork. The patch is
GPL-covered, is not relicensed by the root MPL-2.0 license, and is not packaged
in Android or iOS. The generated `dist/rotorlens-pid-evidence.js` file remains
RotorLens-authored MPL-2.0 source; MPL-2.0 section 3.3 permits its additional
GPL-3.0 distribution as part of that viewer's Larger Work.

## Reserved Phase 2H-A firmware evidence boundary

`integration/rotorflight-firmware/binding-v1/` is the only reserved location for
a future source-reviewed Rotorflight firmware binding patch and its evidence.
It is an integration-review boundary, not a product component: Android packages
only `ui/` and `src/`, and no RotorLens runtime imports this subtree.

The Phase 2H-A boundary now contains one exact GPL-covered partial patch against
Rotorflight 4.6.0 commit
`118e9120260bb33f46df4f92052fb0e9fd4e9ebc`. Its manifest pins the upstream
tree, patch bytes, ten base/result blobs, applied result tree, license, and three
bounded host conformance targets. The implemented slice is only streaming
SHA-256 plus content-only semantic validation and row-TLV encoding of a
caller-provided immutable 103-byte value buffer. It validates every registered
scalar domain and the source-reviewed cross-field rules and rejects invalid
input before calling the writer. It does not build or hash the full binding
preimage, read or capture live firmware state, create or synchronize a
snapshot, or prove the buffer's origin, profile identity, atomicity, or
stability.

The patch also contains an isolated task-context mutation-epoch primitive. Its
unsigned 32-bit generation is even when locally stable, odd across an outer
mutation boundary, and permanently fail-closed at `UINT32_MAX` before wrap. A
separate sticky source-state bit prevents the modeled stale writes of an
NMI/HardFault race from erasing that fault. The host test models those races,
IPSR, PRIMASK, and publication points; it does not execute the real Cortex-M
path or prove target compilation or concurrency. Its simulator branches are
compile-only shims, not SITL synchronization.

The epoch has zero production callers, scoped writer hooks, or capture
consumers. Generation zero proves nothing while every relevant writer is not
covered, and no equal/even/non-fault before/after capture exists. Rotorflight's
source wildcard would include the C file in a target build, so the truthful
boundary is no target-build evidence—not a claim that the file is absent from
target sources. Epoch failure is specified to disable future RotorLens trusted
capture only, never the user's normal configuration mutation.

There is no clean public implementation commit or accepted firmware target, no
target binary or resource measurement, no scoped-writer epoch coverage,
start/terminal atomicity implementation, or real wire capture.
There is no positive runtime registry entry.
The closed partial-candidate schema requires each of those absences and fixes
`runtimeAcceptance` false. A separate runtime-support change is ineligible
until the full source, target, resource, terminal, and independent clean plus
invalidated capture gates in the binding protocol are satisfied.

#### Two defects found after the port, and what they cost

Both were found by re-deriving claims the code made about itself rather than by
a failing test, and both had a fully green suite over them.

**`MAX_SELECTION_DURATION_US` was 120 s on a derivation that did not
reproduce.** The comment justifying it said 120 s was where stationarity ends on
the reference log — "the longest range inside the 12% headspeed gate is 120 s,
13 s in, spread 0.1055". Re-measured from the log's headspeed column at 0.01 s
resolution instead of the 1 s grid that produced it, the longest such range is
**120.781805 s starting 12.74 s in, spread 0.11914**, and 12.73 s in fails at
0.12025. The old cap therefore rejected the reference log's own best range by
0.78 s. Worse, that range's far edge is the last sample in the recording, not
the stationarity gate: extending the end only adds plateau samples, which pushes
the 5th percentile up and the spread down, so the search terminates at the end
of the log rather than at any property of the aircraft. Confirmed by sweeping
every (start, end) pair on a 0.1 s grid — 81,792 evaluations, same answer. The
"120 s" figure was an artefact of a 1 s start grid and a search that never
looked past 120 s because 120 s was already the cap.

The cap is now 262.144 s with a basis that is checkable arithmetic —
`MAX_INPUT_SAMPLES` (262144) expressed as a duration at Rotorflight's nominal
1 kHz logging rate — published as `maximumSelectionDurationBasis` beside the
number. It is a span ceiling, not a stationarity gate. Stationarity is a
property of a particular range, it is measured per range, and it is reported per
range as `rpmEvidence.headspeed.relativeSpread`.

**`harmonicCorrelationAvailability(null)` reported `FIELD_MISSING`.** That
function exists to stop "no rotor explains this peak" being said on a range
where no rotor was checked. Called with no rotor evidence at all — which is
every result that stops before the rotor-speed step — it stamped `FIELD_MISSING`
on both rotors, which is not the absence of a reading but the specific claim
that the log carries no `headspeed` column. The reference log carries one on all
134,429 samples. It committed the exact error it was written to prevent, one
level down.

There are now three states — `evaluated`, `unavailable`, `not-evaluated` — and
`FIELD_MISSING` means one thing only: no finite cell anywhere in the column. A
range where the head was simply stopped reports `NO_VALID_RPM_IN_RANGE`, which
is a fact about the range rather than about the log. The reference log's first
4 s carry 4,028 finite headspeed cells and no admissible rotor speed, and used
to report `FIELD_MISSING` for them.

#### The entry point for a screen

`summarizeMechanicalVibration(sessionOrSeries, {timeRangeUs})` in
`mechanical-spectrum.mjs` is the one call `ui/` should make. It returns a plain
JSON-safe object: per-axis peaks with frequency and amplitude in degrees per
second, whether a rotor harmonic explains each one
(`explained` / `not-explained` / `not-checked`), and the correlation state with
its measured reason where it could not be checked. It contains measurements and
states only; the test suite asserts that no field of it says what to change.

The conversion from UMD to ES modules was done mechanically by a script rather
than retyped, because a transcription slip in analysis code is a measurement bug
and measurement bugs here reach a machine with spinning blades. That script is
also how the viewer's two error strings survived into the first draft of the
mechanical port: a mechanical conversion moves wording as faithfully as it moves
code, so **anything converted by script needs its strings read by a human
afterwards.**

What was deliberately left behind, and must stay behind:

- `flightlog_adapter.js` and `advisor_ui.js` — the first adapts the GPL viewer's
  log objects, the second renders into its UI. Both are the place where
  "derivative work" would be arguable, and both are useless here anyway.
- `cyclic_pid_analysis.js` — the author's own analysis, but written against the
  viewer's `FlightLog` interface. A port of it was written on this branch, in
  five modules, and **deleted before it was ever committed** — see below.
- `rules.js` — see further below.

**`cyclic_pid_analysis.js` stays behind, and the port of it was withdrawn.**
Five modules (`cyclic-capture`, `cyclic-comparison`, `cyclic-evidence-seal`,
`cyclic-session-context`, `cyclic-stop-metrics`, 2,276 lines) existed
uncommitted in the working tree and were removed rather than recorded here as a
transfer. The licensing conditions were not the problem; the measurement was:

- It was a second stop detector beside `src/analysis/records.mjs`, which is the
  one the app calls. The two carried byte-identical constants but only
  `records.mjs` had them re-derived after an early private-development
  correction to the TAG8_4S16 decode, and on the same real log the two returned
  opposite answers about the same two yaw stops.
- Its 80 °/s command threshold was inherited from measurements taken while
  `setpoint[]` was a sawtooth. Post-fix, peak roll setpoint on the reference
  flight is 56 °/s and peak pitch 32 °/s, so **no sample on either axis ever
  reached the threshold** and every cyclic measurement returned null.
- `cyclic-comparison.mjs` documented, correctly, that Rotorflight 4.6 logs do not
  record mixer saturation and that every real comparison is therefore
  inconclusive. That finding is worth keeping. 466 lines whose product answer is
  fixed in advance are not, and it belongs in
  [Blackbox format notes](BLACKBOX_FORMAT_NOTES.md) as a fact about the format.

Deleting it is not a decision that the cyclic measurement is unwanted. It is a
decision that it must be re-derived against the corrected decode the way
`records.mjs` was, rather than restored from a port whose constants were measured
on a bug.

**`rules.js` is not ported, and not merely deferred.** It produces a field named
`recommendation`, 106 times over. Adopting a recommendation engine is a product
decision about what this app is willing to tell someone about their helicopter,
and it had to be made deliberately rather than inherited by a port. It has since
been made — see the next section — and `rules.js` still stays behind: the
decision was to build one against our own evidence and our own gates, not to
import that one. `src/analysis/pid-evidence.mjs` continues to avoid the word,
because it is a measurement module and stays one.

### Decided 12 August 2026: RotorLens recommends what to adjust

**This section was headed "Open decision" and recorded three files answering the
same question three ways. The owner has answered it.** In his words:

> i would like the app to analize the flight log the end user selects and
> recommend what to adjust, thats always been my plan for the app because a lot
> of people have no clue what they are looking at when they see all the info and
> graphs.

That is a deliberate reversal of the rule this repository carried until that
date — *the analysis reports measurements, never instructions* — and it is
recorded **as a reversal**, with its date and its reasoning, rather than quietly
absorbed. A document that contradicts the product is how a future contributor
"restores" a rule nobody meant to keep.

What survived the reversal, unchanged, is listed in [CLAUDE.md](../CLAUDE.md): a
recommendation must be earned by evidence; mechanical faults outrank gains; one
change at a time with the basis shown; confident and wrong is still worse than
silent; and **RotorLens never writes to a flight controller** — not now, not
behind a confirmation.

**The three declarations are not in conflict under that answer. Each is scoped to
what its own module publishes, and all three are correct as they stand:**

| File | What it publishes | Read, after 12 Aug 2026, as |
| --- | --- | --- |
| `mechanical-spectrum.mjs` | `capabilities.settingDirectionAdvice: false`, `tuningRecommendations: false`, on every result | Correct, and now load-bearing rather than merely cautious. The **mechanical** module never advises a gain: its job is to rule the airframe in or out, and it is the gate that outranks every gain conclusion. An airframe module that offered a gain direction would be the exact failure that ranking exists to prevent. |
| `evidence-contract.mjs` | `capabilities.settingDirectionAdvice: true`, `recommendationPolicy.settingAllowlist: ["gov_f_gain"]`, `outputKind: "next-controlled-test"`, `directSettingWrites: false`, `finalTuneClaims: false` | Correct. This is the **product-level** policy, and it is the one that changed meaning: advice is permitted, for allowlisted settings only, phrased as the next controlled test rather than a finished tune, and never as a write. |
| `deterministic-metrics.mjs`, line 577 | a field named `direction`, values `"increase"` and `"decrease"`, `null` unless `sufficient` | Correct. It is the **gated input** a recommendation is built from, not a published verdict — note it is already `null` whenever the evidence is insufficient, which is the same rule the five gates apply one level up. |

So the shape of the answer is: the mechanical module measures and gates, the
metrics module produces a direction only where its own evidence is sufficient,
the evidence contract states the policy, and `src/analysis/recommendations.mjs`
— behind the five gates in `src/analysis/advisor/recommendation-gates.mjs` — is
the only place any of it becomes a sentence telling a pilot to change something.
`test/axis-report.test.mjs` enforces that single route by reading every string
literal in every module under `src/`.

**Two consequences, neither of which may happen silently:**

1. `recommendationPolicy.settingAllowlist` is `["gov_f_gain"]`, which was the one
   setting the ported metrics could support. The gain path now being built
   reaches beyond it. **Widening that allowlist is an owner decision, one setting
   at a time, recorded in this document with the evidence that earns each
   entry** — not a list that grows because a module needed it to.
2. `test/advisor-mechanical.test.mjs` contains "the settingDirectionAdvice
   conflict is pinned exactly as it stands", which asserts the three
   declarations *as a conflict* and cites this section as recording it open.
   Every value it pins is still the value the product wants, so it is still
   green and still useful — but its name and its comment describe a state of
   affairs that no longer exists. **Rename it and rewrite its comment** to say
   what it now pins: three correctly scoped declarations, and an allowlist that
   may only widen through this document.

### Amended 13 August 2026: "mechanical faults outrank gains" was not actually holding

The 12 August decision kept four engineering constraints intact, one of which was
that a mechanical fault outranks a gain. An adversarial review found four
separate paths where it did not, each reproducible with a physically plausible
machine, each ending in a confident gain instruction with `actNow` set. They are
recorded here because the fixes add limits to the engine, and a limit without a
reason written down is a number waiting to be tuned away.

| What the aircraft actually had | What the engine said | What now stops it |
| --- | --- | --- |
| A control run at its travel limit — a servo horn on the wrong hole, a linkage set short | "Raise P", at every gain, unfalsifiably. Tripling P moved the tracking error by 0.16% | `AUTHORITY_LIMITS.standingOffsetShareOfCommand`. A shortfall larger than a gain step can close is not a gain finding; it falls through to `AXIS_DOES_NOT_ARREST`, whose candidate list already named the travel limit |
| A binding tail, with the flight controller's own `iterm_limit` doing its job | "Raise yaw I", identically at four clamp values, on the same 22 deg/s standing error | `AUTHORITY_LIMITS.iTermTravelShare`. An unsaturated integrator facing a standing error *must* move — it is the running total of that error. Large and frozen is a clamp |
| A hunting governor, a slipping belt, wind | "Lower yaw I", down to a tenth of the original. Removing I entirely changed the wander from 23.9 to 23.8 deg/s | `AUTHORITY_LIMITS.iTermShareOfOutputRipple`. The crossing-rate match reads ~1.0 for *any* external periodic input, because the integral of a periodic error is periodic at the same frequency. Size is what makes the confirming flight's promise keepable |
| A tone the spectrum analyser had positively matched to main-rotor order 1, sitting under the 8 deg/s attention threshold | "Lower roll D" — while telling the pilot the airframe was "a positive measurement of absence, not silence" | `TONE_LIMITS`, and `AIRFRAME_TONE_BELOW_ATTENTION` replacing `AIRFRAME_CLEAR` whenever a sub-threshold tone was measured |

**The tone rule is deliberately narrow, and the narrowing is the interesting
part.** The first draft refused a gain change whenever any persistent tone
coincided with the oscillation. That is wrong: a control loop oscillating after
every release *is* a persistent narrowband tone in the gyro — measured on this
repository's own too-much-D fixture it reads 25.4 Hz, 4.8 deg/s, present in 82%
of the analysis windows, indistinguishable in every published field from a
structural mode. That rule would have refused every genuine D and P finding
forever. What a loop cannot do is choose to oscillate at exactly the rotor's own
turning speed, so only a **rotor-order match** blocks.

The cost is stated rather than hidden, and it is real: a genuine D fault whose
ringing lands on a rotor order is refused a verdict and sent away to fly the same
stops at a different head speed. `test/recommendations.test.mjs` pins both sides —
the refusal on the order, and the same fault a few Hz away still earning "lower
D". A NON-rotor mechanical mode below the attention threshold at the frequency of
the ring is still not separable from a D fault within one log, and is still read
as one. That is a limit of one flight rather than of the code, and the flight
that settles it is the one the finding prescribes.

**Separately, `pid-evidence.mjs` now drops a steady segment that begins at the
first sample it was given** (`CLIPPED_BY_WINDOW`). The flight window went live in
the UI the same week, so the first sample is wherever the takeoff trim landed.
Sweeping that trim across the reference flight made roll's I-term evidence read
captured / 2 holds at 18, 20, 22.76 and 24 seconds and inconclusive / 1 at 0 and
26 — non-monotonically, with the detected window sitting inside the captured
region. Only the START edge is dropped: a hold running to the last sample was
entered from a command change the records contain, so its settle skip is real and
every number inside it is measured over fully observed samples.

## Components

```text
owned log bytes
        |
        v
RotorLens Blackbox decoder (src/blackbox/, ours, MPL-2.0)
        |
        v
RotorLens parser contract (app-owned normalized records)
        |
        +--> session/field summary
        +--> graphs and deterministic analysis
        +--> gated local recommendations
```

`src/parser-contract.mjs` is the stable application boundary. A future native or
WASM adapter owns all translation from engine types. UI and analysis code must
depend on the normalized contract rather than any engine's internals — that is
what keeps the engine choice reversible.

`src/blackbox/` is the decoder: bounds-checked reader, field encodings,
predictors, header tables, and the frame loop. It is written from the log format
and shares its header parser with `src/fixture-preflight.mjs`, so a fast header
inventory can never disagree with a full decode. Its format assumptions and
verification status are recorded in [Blackbox format notes](BLACKBOX_FORMAT_NOTES.md).

`src/analysis/advisor/` is reachable from the UI only through the designated
recommendation boundary. `ui/app.mjs` builds normalized records and mechanical
evidence, dynamically loads `src/analysis/recommendations.mjs`, and renders the
result in **What to adjust**. The recommendation module calls the five-gate
interlock in `src/analysis/advisor/recommendation-gates.mjs`; the UI does not
reimplement or bypass those decisions. `src/analysis/records.mjs` and
`src/analysis/pid-evidence.mjs` remain measurement modules rather than advice
publishers.

The mechanical spectrum now has one documented door for a screen to come in by,
`summarizeMechanicalVibration`, so that wiring it does not mean a UI learning
the shape of a Welch quality block. That door publishes measurements and states
only — under the decision above, the mechanical module advises nothing, and the
sentence a pilot reads about his airframe is composed one level up.

## Dependencies

The browser/Node engine has no npm or Cargo dependency, and
`config/parser-engine-decision.json` records the adopted decoder as our own. The
Android shell bundles the permissively licensed components pinned by Gradle;
`android/shipping-dependencies.json`, `THIRD_PARTY_NOTICES.md`, and the generated
in-app Legal screen enumerate the resolved distribution rather than pretending
the transitive runtime is absent.

Adopting anything requires a license and provenance review, an entry in
`THIRD_PARTY_NOTICES.md`, and a pin to a full commit hash — never a branch or a
floating tag. `test/provenance.test.mjs` fails the build if a component is
adopted without its notice.

## Safety boundary

Rewritten 12 August 2026, with the decision above.

Parsing and deterministic measurements run locally. **Tuning advice is now part
of the product**, and every piece of it must cite the measurement it rests on,
state its confidence, say what is missing when the data is incomplete, and be
one change at a time. Where the evidence does not separate the candidate causes,
the output is what can be seen plus what to fly to settle it — never a guess
presented as a verdict. Mechanical faults outrank gains: a gain conclusion on an
airframe that was never ruled out is worse than no conclusion, and the airframe
gate in `src/analysis/advisor/recommendation-gates.mjs` is what enforces that
ordering.

**RotorLens never writes to a flight controller.** Not silently, not behind a
confirmation, not with per-action consent. There is no write path, so there is
no dialog anyone can be talked through. The previous wording of this section —
"must not *silently* write settings" — left room for one and is the reason this
paragraph is now explicit. `test/axis-report.test.mjs` asserts that no module
under `src/` reaches for a serial, USB, Bluetooth or HID transport, and that
every `directSettingWrites` declaration in the engine is `false`.
